# 034 — API

## Vision

One JSON-RPC 2.0 API, over HTTP (`/api/rpc`) and WebSocket (`/ws`), used identically by
every shell — the concrete mechanism behind "one Core, many surfaces" (Part 15).

## Goals

Full method inventory by domain (all in `cid-core/src/api/router.rs`'s dispatch table):

- **Workspace/Repo/Session**: `workspace.*`, `repo.*`, `session.*`, `message.list`
- **Git**: `git.*` (status, diff, commit, log, worktree.*, hunk.apply)
- **PTY**: `pty.*`
- **MCP**: `mcp.*`, `mcp.task.*`
- **Model routing**: `model.*`, `local.runtime.*`, `background_model.*`
- **Planner/Reviewer**: `session.plan.*`, `session.review.*`
- **Skills**: `skills.*`
- **ACP**: `acp.*`
- **Context/Semantic Engine**: `context_engine.*`, `semantic_engine.*`,
  `semantic_engine.test_impact.*`, `semantic_engine.docs.*`
- **Code analysis**: `code.*`
- **Subagents**: `subagent.*`
- **Bridges**: `github.*`, `forge.*`, `tracker.*`, `slack.*`, `teams.*`
- **Autonomy**: `autonomy.*`
- **Sandbox**: `sandbox.*`
- **Accounts/roles**: `auth.*`
- **Governance**: `governance.*`
- **Confidence**: `confidence.*`
- **Role profiles**: `role_profile.*`
- **Decisions/Deployment**: `decisions.*`, `deployment.*`
- **Settings**: `settings.*`

Every method returns `{ jsonrpc: "2.0", id, result }` on success or
`{ jsonrpc: "2.0", id, error: { code, message } }` on failure — a malformed request or
unknown method never returns a 5xx, always an orderly JSON-RPC error (verified across
`tests/protocol_fuzz.rs`).

## Non-Goals

REST or gRPC alongside JSON-RPC — Part 18 decided this deliberately (matching the wire
style MCP and ACP already use), not left open for per-endpoint choice.

## Architecture

`handle_rpc` (`api/router.rs`) is a single large `match method.as_str()` dispatch —
chosen over a router-per-domain split for straightforward greppability at the current
method count (~150+), revisit if it becomes unwieldy.

## Data Structures

`JsonRpcRequest`, `JsonRpcResponse`, `JsonRpcNotification` (`api/types.rs`).

## Traits / Interfaces

`http_rpc_handler` (HTTP POST) and `handle_ws` (WebSocket) both funnel into the same
`handle_rpc` — one dispatch implementation, two transports.

## Storage Layout

N/A — the API layer is stateless; state lives in the managers it dispatches to.

## Performance Targets

100 concurrent RPC calls complete in 26ms, 100/100 succeeding
(`one_hundred_concurrent_rpc_calls_all_complete`).

## Tradeoffs

No API versioning scheme exists — method names are added, not versioned
(`session.plan.generate` rather than `session.plan.generate.v2`). Acceptable while CID
has no external third-party API consumers; would need reconsideration if that changes.

## Failure Modes

Deeply nested JSON, arbitrary method names, and arbitrary parameter shapes against every
real method category are all handled without a 5xx or a panic — the specific property
`tests/protocol_fuzz.rs` exists to verify, using `proptest` for the arbitrary-input cases.

## Security

Every method (except `/health`) is subject to `access::AccessPolicy`'s bearer-token check
when Core is non-loopback-bound (`031-Security.md`). Governance- and auth-scoped methods
additionally require a valid session token as a parameter.

## Testing

56 integration tests in `cid-core/tests/api_integration.rs` exercise the real dispatch
table over HTTP; 9 fuzz tests in `tests/protocol_fuzz.rs` exercise the boundary against
hostile input.

## Implementation Order

Core dispatch shape fixed in Phase 0; every phase since has added methods to the same
table without restructuring it.

## Acceptance Criteria

Every RPC method has at least one test exercising it over real HTTP/WS, not just a
handler-function unit test.

## AI Coding Rules

New RPC methods go in the `match` block in `handle_rpc`, with a corresponding
`handle_<name>` function and — per this project's own consistent pattern — a
`required_str` call for mandatory string params rather than manual `Option` unwrapping,
so a missing parameter produces a clear "X is required" error instead of a generic serde
failure.
